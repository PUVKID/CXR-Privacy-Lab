## Fix4 — 실제 6차 실행 트리의 Python 런 타임 불일치와 중첩 학습 실행

- 사용자 PowerShell 전체 프로세스 트리에서 6차 재개 관리자 운영 관리자 A(E: Python) → 운영 관리자 B(Codex 런타임 Python), 6차 학습 실행 운영 학습 A(E: Python) → 운영 학습 B(Codex 런타임 Python), Windows 콘솔 운영 콘솔 A(운영 관리자 A의 자식), 운영 콘솔 B(운영 학습 A의 자식)을 확인했습니다. 총 **6개 관련 프로세스**입니다.
- PID 운영 학습 B는 첫 번째 학습 실행 운영 학습 A의 자식으로서 **동일한 `5차\실험 코드\train_from_scratch.py`, 동일한 대상 RunID 출력 폴더와 나머지 학습 인수**를 사용하지만 Python 바이너리 경로만 다릅니다. 기존 중지 대상 판별기는 E: Python 실행만 학습으로 인정하여 이 프로세스를 `An unrecognized descendant`로 거부했습니다.
- 이번 변경은 E:의 정확한 대상 학습 실행을 기준으로 **검증된 관리자 또는 원본 학습 아래에서 동일한 전체 학습 인수를 사용하는 Python 실행**을 추가 학습 대상으로 확인합니다. 해당 프로세스의 PID·부모 관계·실행 파일·전체 명령 행·생성 시각을 각각 유지하고, 실제 중지 직전에도 PowerShell에서 PID 재사용과 정체 변화를 검사합니다. 확인되지 않은 위치에서 동일 출력 경로를 주장하는 실행, 다른 seed/인수, 실행 파일과 명령 행이 맞지 않는 실행은 자동 중지를 거부합니다.
- 실제 6개 프로세스를 재현한 테스트는 변경 전 PID 운영 학습 B에서 실패했고 수정 후 관리자 `[운영관리자A, 운영관리자B]`, 학습 `[운영학습A, 운영학습B]`, 작업자 `[]`를 반환합니다. 두 콘솔 호스트는 종료 목록에 포함되지 않습니다. 이러한 프로세스들이 이후에도 항상 같은 형태로 실행된다는 의미는 아닙니다.
- 루트 Python **85개 테스트 통과**, PowerShell·설치기·CMD 부트스트랩 코드 검사 통과. 사용자 Windows에서 실제 6차 중지와 7차 시작까지는 아직 검증되지 않았으며, 기존 데이터·체크포인트는 삭제하지 않습니다.

## Fix3 — 중첩된 6차 재개 관리자·실제 학습 프로세스의 콘솔 호스트 처리

- 추가로 제공된 실제 Windows CIM 출력에서 두 단계의 6차 재개 관리자(PID 운영 관리자 A → PID 운영 관리자 B)가 확인되었습니다. PID 운영 관리자 B은 Codex Python 런타임에서 `6차\work\CXR6_EONLY_Resume.py`를 실행하고, 그 자식 PID 운영 학습 A가 E: 의 `5차\실험 코드\train_from_scratch.py`로 대상 RunID의 학습을 실행하고 있었습니다. PID 운영 콘솔 B은 **이 실제 학습 프로세스의 직속 `C:\WINDOWS\system32\conhost.exe`**로, 명령행 `\??\C:\WINDOWS\system32\conhost.exe 0x4`, 생성 시각 정밀운영시각비공개(KST)이었습니다.
- Fix2는 검증된 관리자 아래 `conhost.exe`만 허용해서, 학습 프로세스 아래 콘솔 호스트를 잘못 거부했습니다. 두 중첩 관리자·실제 학습·두 개의 `conhost.exe`를 CIM 순서와 무관하게 재현한 테스트는 수정 전 PID 운영 콘솔 B의 `An unrecognized descendant` 오류로 실패했습니다.
- Fix3는 **엄격히 식별된 6차 관리자·해당 RunID 학습 프로세스·검증된 Python multiprocessing 작업자** 바로 아래의 OS 콘솔 호스트만 *종료 목록에서 제외*합니다. 정확한 시스템 실행 경로, 네이티브 명령행, 비어 있지 않은 생성 시각을 확인하고, 파일·명령행이 다른 유사 프로세스 또는 콘솔 호스트가 시작한 미확인 자식은 계속 차단합니다. 이러한 콘솔 호스트를 중지 대상으로 분류하거나 종료하지 않습니다.
- 수정 전 실패를 확인한 회귀 테스트 세 개가 수정 후 통과했고, 전체 Python **79개 테스트가 모두 통과**했습니다. Windows 실 제 6차 중지·7차 RTX4090 신규 학습 완료·원 논문 성능 재현은 사용자 PC에서 아직 검증되지 않았습니다.

## Fix2 — 6차 관리자 콘솔 호스트 오인 수정

- 사용자 CIM 출력에서 PID 운영 콘솔 A은 `C:\WINDOWS\system32\conhost.exe`였으며, 부모 PID 운영 관리자 A은 `6차\work\CXR6_EONLY_Resume.py`를 실행하는 Python 재개 관리자였습니다. 두 프로세스의 표시상 생성 시각은 정밀운영시각비공개(KST)입니다.
- 기존 중지 대상 검증기가 인증된 관리자의 자식을 Python multiprocessing 작업자로만 허용하여, 해당 콘솔 호스트를 `An unrecognized descendant (PID 운영콘솔A)` 오류로 거부한 사실을 테스트로 재현했습니다.
- 수정된 예외는 **검증된 6차 관리자 직속 자식**이면서, 실제 실행 파일이 정확히 `C:\Windows\System32\conhost.exe`이고, 명령행이 Windows 기본 네이티브 실행형 `\??\C:\WINDOWS\system32\conhost.exe 0x<16진수>`인 경우에만 적용합니다. 이 콘솔 호스트는 **종료 명단에 절대 포함하지 않습니다**. 실제 파일 경로·명령행·부모가 다른 경우와 콘솔 호스트 아래 별도 자식이 관측되는 경우는 계속 차단합니다.
- 실패하는 재현 회귀 테스트를 먼저 실행하고, 변경 후에는 해당 테스트 및 위장/비정상 자식 거부 테스트가 통과함을 확인했습니다. Python 전체 **76개 테스트**, PowerShell 실행기·설치기, CMD 부트스트랩 검사도 재실행했습니다.
- 6차 관리자와 학습 프로세스의 PID뿐 아니라 생성 시각·실행 경로·전체 명령 행을 각각 재확인하는 보호 절차는 유지했습니다. 6차 체크포인트/기존 데이터 삭제 기능을 추가하지 않았습니다. 사용자 Windows에서 실제 중지가 성공했는지, RTX 4090에서 7차 훈련이 시작됐는지는 아직 확인되지 않았습니다.

## Fix1 — Windows 줄바꿈 사전 검사 수정

- 사용자 Windows 실행 로그에서 설치와 CUDA 런타임 import는 성공했지만, 72개 사전 검사 중 `test_cmd_contains_complete_checksum_verified_payload` 1개가 실패했습니다. `Path.write_text`가 만든 CRLF 파일을 LF 고정 문자열과 비교한 테스트의 오류였습니다. 패키징은 원본 바이트를 올바르게 보존했습니다.
- 수정 전, 명시적 CRLF fixture로 같은 AssertionError를 재현했습니다. 수정 후에는 빌드 전에 읽어 둔 실제 원본 바이트와 압축 결과를 정확히 비교하며, LF와 CRLF 두 회귀 검사를 추가했습니다. 검사 생략이나 줄 바꿈을 무시하는 비교는 넣지 않았습니다.
- 수정 후 전체 **74개 테스트 통과(10.293초, Linux CPU)**. PowerShell 실행기·설치기 행동 검사와 생성 CMD 부트스트랩 검사도 다시 통과했습니다. 이는 수정본의 Windows 전체 실행 또는 실제 GPU 학습 완료를 뜻하지 않습니다.
- 이전 배포 ZIP과 대조한 학습·평가 코드 및 CMD/PowerShell·빌더 **122개 파일의 바이트가 모두 동일**합니다. 이번 수정은 배포 테스트와 이 검증 기록뿐입니다.
- 사용자 로그의 실패 지점은 `Check-Prerequisites` 내부입니다. 다음 단계인 `Stop-SixthRun`에 도달하지 않았으므로 해당 실행은 6차 중지나 7차 본 학습을 시작하지 않았습니다. `work/temp` 아래 `[EXAMPLE]` 출력은 사전 검사 임시 자료입니다.
- 새 CMD를 내려받아 기본 `start`로 실행하면 기존 7차 코드는 백업 후 갱신하고, 다시 사전 검사를 거칩니다. 기존 데이터와 runs는 삭제하지 않습니다. 모든 사전 검사를 통과한 다음에만 대상 6차 중지 절차가 진행됩니다.
